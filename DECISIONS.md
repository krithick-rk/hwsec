# Architectural Decisions

## Phase 1
1. **Language Choice**: Implemented in modern JavaScript (ESModules) running on Node.js. Given the lack of Python in the environment, Node.js provides a ubiquitous, lightweight runtime well-suited for CLI applications.
2. **CLI Framework**: Used `commander` for robust CLI argument parsing and `--help` generation.
3. **Schema Engine**: Defined schemas using JSDoc typings (`src/core/schema.js`) in JavaScript to provide strict typings while avoiding the compilation overhead of TypeScript in this bootstrap phase.
4. **Planning Safety**: The `Planner` aggressively builds paths and checks files but relies strictly on the `Workspace` abstraction to avoid writing files outside the auditable `hwsec-output/` directory.
5. **Tool Abstraction**: Created `ToolAdapter` base class that natively wraps external binaries (Verilator, Yosys, AFL++) and normalizes their outputs into the shared Finding/Evidence JSON schema.

## Environment Boundaries & Execution Rules
6. **Heterogeneous Toolchain Orchestration**:
   - **Windows / OSS CAD Suite**: Hosts deterministic hardware verification tools (Yosys, SymbiYosys `sby`, Verilator).
   - **WSL2 / Ubuntu**: Hosts fuzzing infrastructure (AFL++: `afl-fuzz`, `afl-cc`, `afl-clang-fast`).
   - The orchestrator explicitly manages the Windows ↔ WSL2 boundary (path translation `/mnt/...` vs `E:\...`, runtime detection) rather than assuming single-environment tool availability.
7. **AFL++ Compilation & Fuzzing Pipeline**:
   - Compiles C++ simulation harnesses generated by Verilator using AFL++ LLVM instrumentation (`afl-cc` / `afl-clang-fast`) inside WSL2.
   - Avoids directly instrumenting Verilator binary itself.
8. **Deterministic Tool Invocations & Logging**:
   - Every tool execution records: tool version, runtime environment (Windows vs WSL), full command, stdout/stderr, exit code, and timeout.
   - Non-zero exit codes, compiler/lint warnings, or solver timeouts are recorded strictly as **execution telemetry / tool failures**, never misclassified as security findings without artifact-based verification.
9. **Planning & Safety Invariants**:
   - The `analyze` phase is strictly zero-execution / non-destructive (no fuzzing, formal proofs, long simulation, or costly LLM calls).
   - Analysis plans require explicit user confirmation (`proceed <analysis-id>`).
   - Independent tool/worker failures must fail gracefully without corrupting the workspace or blocking other analysis workers.
   - System configs and third-party tools (e.g. OSS CAD Suite installation scripts) are never modified, overwritten, or run with unauthorized `sudo`.
